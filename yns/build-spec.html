Technical build specification

What each phase covers, how the underlying systems are structured, and how the design and implementation work relates to the infrastructure the site runs on.

The infrastructure is inexpensive. The implementation isn't.

Phase 1 ₹75,000 Landing, genre worlds, design system
Phase 2 ₹1,25,000 Commerce system, Razorpay, accounts
Total ₹2,00,000 Both phases, one build

Phase 1 — Community launch

₹75,000

Builds and ships the landing experience, the three genre worlds, the community content within them, and the foundation the site runs on. No commerce in this phase.

Experience architecture

"What's your vibe?" entry

Blank landing prompt — no retail or product content is shown until a genre is chosen.

Three genre pathways

Psychedelic, house/disco, and techno — each a distinct route into its own world, not a filter applied to one shared page.

Genre-specific worlds

Each pathway leads to a retail-facing world with its own visual treatment and content, built on one shared design system.

Retail / community relationship

Community content — DJs, angels, etiquette, safety — is reachable from inside each genre-world rather than living as a separate top-level section.

Omi's Club cross-navigation

Omi's Club lives at yasandsass.in/omisclub as its own branded subpath, cross-linked with the genre-worlds — one domain, two brand presentations, shared navigation.

Responsive behavior

The entry flow, genre routing, and every genre-world are built for phone, tablet, and desktop, not designed for one and adapted after.

Information architecture

Defines how a visitor moves from an unbranded entry point through a genre choice into a fully-styled world and back out to community content and Omi's Club — a structure the routing and navigation are built against.

Design system implementation

Typography and spacing rules

Applied consistently across the landing, genre worlds, and community sections rather than set per page.

Reusable UI components

Navigation, cards, section layouts, and buttons built once and shared across all three genre worlds.

Genre-specific visual treatments

Each world carries its own mood within the shared system, distinguishing psychedelic, house/disco, and techno without three separate design languages.

Navigation and interaction states

Hover, focus, active, and menu open/closed states defined once and reused everywhere.

Responsive components

The same components adapt across breakpoints, rather than shipping separate mobile and desktop markup.

Black/white base with iridescent landing shine

The agreed visual direction, implemented as a moving iridescent effect confined to the landing background — a built interaction, not a static asset.

Genre-cue imagery on vibe selection

Small pop-up visuals per genre alongside the word-led selection — not a blank text list, not a busy photo grid.

Video-based clothing presentation

Clothing shown as video rather than static photography across the genre-worlds — a presentation decision that touches both the design system and the media pipeline below.

Content / data architecture

What the application needs to represent: genres, the DJs/angels/etiquette/safety content tied to each one, and — from Phase 2 — the products associated with each genre. Genre and community content is stored as data in Supabase rather than hardcoded into page markup, so it can be updated by editing rows directly in the database, without a code deploy. This is a data model, not a content-management interface — there's no separate admin screen; edits happen in Supabase itself. Page structure, navigation, and design-system components remain frontend code.

Genre records

The three genres as structured entries, not hardcoded strings scattered across pages.

Community content per genre

DJ bios, angels, etiquette, and safety information, each related to the genre-world it belongs to.

Genre-to-content relationships

Modeled in the schema so each world's page only retrieves and displays what's relevant to it.

Media implementation

YouTube-sourced audio/video

Used instead of self-hosted media to keep page weight and hosting cost down.

Context-aware playback strategy

Ambient background audio and featured content are embedded and loaded differently, rather than using one generic embed everywhere.

Video-based clothing loading

Video is heavier than static images; genre-world pages need their own loading approach so they stay responsive with video product presentation in place.

Pre-roll mute window

An already-scoped workaround that mutes YouTube's pre-roll ad audio on embedded playlists for a fixed window, then unmutes for real content. It does not detect or block ads — it's a narrow playback fix, not a general ad-blocking system.

Application foundation

Supabase project setup

Schema design for genres and community content, table relationships, and initial Postgres configuration.

Vercel project setup

Environment variables, build configuration, and git-based deployment, so pushes to the repository publish automatically.

Domain and subpath routing

yasandsass.in serves the main site; /omisclub is a routed subpath with its own branding, not a separate domain or a separate deploy.

No customer auth in this phase

Authentication is not part of Phase 1 — it begins in Phase 2, alongside the shop.

QA / delivery

Responsive testing

Phone, tablet, and desktop, across the entry flow, all three genre-worlds, and community sections.

Navigation / user-flow testing

Vibe selection → genre-world → community content → cross-nav into Omi's Club, and back.

Content / data testing

Each genre-world correctly retrieves and displays only its own DJs, events, and safety content.

Deployment testing

Verified against the actual Vercel + Supabase configuration, not just local development.

Launch readiness

Fixes from testing applied, and sign-off that the Phase 1 site is ready to show or launch.

Phase 2 — Commerce launch

₹1,25,000

Adds the retail layer once product is ready to ship: catalog, cart, checkout, payment, accounts, and orders — built on top of the Phase 1 foundation.

Product system

Products and variants

Size/color as applicable, with stock counts per variant.

Genre relationships

Each product is associated with a genre-world, so it appears in the correct retail context.

Product media

Video presentation, per the agreed clothing-as-video direction.

Product state

In stock, out of stock, or hidden, reflected in what's shown to a shopper.

Shopping flow

Product discovery within a genre-world → product detail → variant selection → cart → quantity/state management → checkout → payment → confirmation. This is the flow being built; anything beyond it — wishlists, reviews, recommendations — is out of scope unless separately agreed.

Payment integration

Razorpay handles the payment transaction itself. The development work is everything around it.

Checkout initiation

Moving a cart into a payable checkout session.

Payment handling and verification

Handling the return from Razorpay and verifying the payment server-side, rather than trusting the client.

Success / failure states

Shopper-facing outcomes for both a confirmed and a declined or interrupted payment.

Order creation tied to verified payment

An order exists once payment is confirmed — not on cart submission alone.

Test/staging and production configuration

Separate Razorpay configuration so the payment flow is exercised before it touches real transactions.

Customer accounts

Supabase Authentication provides sign-in. The development work is wiring it into the shop.

Authenticated vs. anonymous state

The shop behaves correctly whether or not a shopper is signed in.

Customer profile

Profile fields scoped to the signed-in user.

Order history

Gated behind sign-in, scoped to that customer's own orders.

Order system

Orders and line items

Each order records what was bought, tied to the customer who bought it.

Payment and inventory relationship

A completed order reflects both a confirmed payment and a stock deduction.

Order state

Scoped to what the Phase 2 shop needs (e.g. paid, fulfilled) — not a full order-management back office.

Production / QA

Staging environment

The full purchase flow, including Razorpay, exercised before it's live.

Production deployment

Once staging is signed off.

Integration testing

Product, cart, checkout, payment, and order creation tested together, not only in isolation.

Payment testing

Successful, failed, and declined payments, and the resulting order and shopper-facing states for each.

Error handling and launch support

Interrupted or failed payments handled gracefully; support through the shop's launch.

Infrastructure vs. implementation

The services below are separate from the development fee. They're the platforms the application is built on and, in some cases, carry their own ongoing or per-transaction cost — set by those providers, not by this project.

Infrastructure

  • Vercel — hosting/deployment platform. The initial build runs on its free tier.
  • Supabase — database, auth, and backend services. The initial build runs on its free tier; as traffic and, later, commerce volume grow, this typically moves to a paid tier, priced by Supabase and scaled to the site's own usage — separate from this quote.
  • Razorpay — payment infrastructure, with a per-transaction fee set by Razorpay.
  • YouTube — external media hosting for audio/video.
  • Domain — the existing yasandsass.in registration.

Implementation

  • Information architecture and experience design
  • Design system implementation across genre-worlds
  • Database/schema design and data relationships
  • Application logic connecting the frontend to Supabase
  • Frontend implementation of every screen and component
  • Third-party integrations (YouTube; Razorpay in Phase 2)
  • Authentication and account wiring (Phase 2)
  • Commerce flows — product, cart, checkout, orders (Phase 2)
  • Payment and order-state logic (Phase 2)
  • Responsive behavior across breakpoints
  • Testing across devices, flows, data, and integrations
  • Deployment configuration and production delivery

What the development fee covers

The quoted development fees are for the design and implementation of the application, not for the underlying third-party services. Vercel, Supabase, Razorpay, and YouTube are infrastructure — the same infrastructure nearly any comparable product would sit on. The development work is in designing the architecture around those services: implementing the experience and, in Phase 2, commerce flows described above, connecting genre and content data — and later product, order, and payment data — to the interface, handling application and payment state, testing the complete experience across devices and flows, and deploying a functioning production system.

The cost is therefore not set by the number of pages or by the retail price of the software services being used. It reflects the systems being designed and implemented in each phase, and the responsibility for delivering them as a working product — including the testing and fixes that happen before and after launch.
