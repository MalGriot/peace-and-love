How I'm building this

What I'm delivering in each phase, how I've structured the systems underneath it, and how my design and implementation work relates to the infrastructure the site runs on.

My philosophy: inexpensive infrastructure + high-equity implementation.

Phase 1 ₹75,000 Landing, genre worlds, design system
Phase 2 ₹1,25,000 Commerce system, Razorpay, accounts
Total ₹2,00,000 Both phases, one build

Phase 1: Community launch

₹75,000

I'm building and shipping the landing experience, the three genre worlds, the community content inside them, and the foundation the site runs on. No commerce in this phase.

Experience architecture

"What's your vibe?" entry

I start with a blank prompt. No retail or product content shows until a genre is chosen.

Three genre pathways

I route psychedelic, house/disco, and techno as three distinct paths into their own world, not as a filter on one shared page.

Genre-specific worlds

Each pathway leads to a retail-facing world I build with its own visual treatment and content, on one shared design system.

Retail / community relationship

I make community content (DJs, angels, etiquette, safety) reachable from inside each genre-world, rather than a separate top-level section.

Omi's Club cross-navigation

I'm placing Omi's Club at yasandsass.in/omisclub as its own branded subpath, cross-linked with the genre-worlds: one domain, two brand presentations, shared navigation.

Responsive behavior

I build the entry flow, genre routing, and every genre-world for phone, tablet, and desktop from the start, not designed for one and adapted after.

Information architecture

I define how a visitor moves from an unbranded entry point through a genre choice into a fully-styled world and back out to community content and Omi's Club, then build the routing and navigation against that structure.

Design system implementation

Typography and spacing rules

I apply these consistently across the landing, genre worlds, and community sections, rather than setting them per page.

Reusable UI components

I build navigation, cards, section layouts, and buttons once and share them across all three genre worlds.

Genre-specific visual treatments

I give each world its own mood within the shared system, distinguishing psychedelic, house/disco, and techno without three separate design languages.

Navigation and interaction states

I define hover, focus, active, and menu open/closed states once and reuse them everywhere.

Responsive components

I build components to adapt across breakpoints, rather than shipping separate mobile and desktop markup.

Black/white base with iridescent landing shine

I'm implementing the agreed visual direction as a moving iridescent effect confined to the landing background, a built interaction, not a static asset.

Genre-cue imagery on vibe selection

I pair small pop-up visuals per genre with the word-led selection, not a blank text list, not a busy photo grid.

Video-based clothing presentation

I show clothing as video rather than static photography across the genre-worlds, a decision that touches both the design system and the media pipeline below.

Content / data architecture

I model what the application needs to represent: genres, the DJs/angels/etiquette/safety content tied to each one, and, from Phase 2, the products associated with each genre. I store genre and community content as data in Supabase rather than hardcoding it into page markup, so it can be updated by editing rows directly in the database, without a code deploy. That's a data model, not a content-management interface: there's no separate admin screen; edits happen in Supabase itself. Page structure, navigation, and design-system components stay frontend code.

Genre records

I model the three genres as structured entries, not hardcoded strings scattered across pages.

Community content per genre

I relate DJ bios, angels, etiquette, and safety information to the genre-world each one belongs to.

Genre-to-content relationships

I model these in the schema so each world's page retrieves and displays only what's relevant to it.

Media implementation

YouTube-sourced audio/video

I use YouTube instead of self-hosted media to keep page weight and hosting cost down.

Context-aware playback strategy

I embed and load ambient background audio differently from featured content, rather than using one generic embed everywhere.

Video-based clothing loading

Video is heavier than static images, so I give genre-world pages their own loading approach to keep them responsive with video product presentation in place.

Pre-roll mute window

I already scoped and built a workaround that mutes YouTube's pre-roll ad audio on embedded playlists for a fixed window, then unmutes for real content. It doesn't detect or block ads. It's a narrow playback fix, not a general ad-blocking system.

Application foundation

Supabase project setup

I design the schema for genres and community content, the table relationships, and the initial Postgres configuration.

Vercel project setup

I configure environment variables and the build, and wire up git-based deployment so pushes to the repository publish automatically.

Domain and subpath routing

I serve the main site from yasandsass.in and route /omisclub as a subpath with its own branding, not a separate domain or a separate deploy.

No customer auth in this phase

I'm not building authentication in Phase 1. It starts in Phase 2, alongside the shop.

QA / delivery

Responsive testing

I test phone, tablet, and desktop across the entry flow, all three genre-worlds, and community sections.

Navigation / user-flow testing

I test vibe selection into genre-world into community content into cross-nav into Omi's Club, and back.

Content / data testing

I confirm each genre-world retrieves and displays only its own DJs, events, and safety content.

Deployment testing

I verify this against the actual Vercel and Supabase configuration, not just local development.

Launch readiness

I apply fixes from testing and sign off that the Phase 1 site is ready to show or launch.

Phase 2: Commerce launch

₹1,25,000

Once product is ready to ship, I add the retail layer: catalog, cart, checkout, payment, accounts, and orders, built on top of the Phase 1 foundation.

Product system

Products and variants

I build size/color variants as applicable, with stock counts per variant.

Genre relationships

I associate each product with a genre-world, so it appears in the correct retail context.

Product media

I give each product video presentation, per the agreed clothing-as-video direction.

Product state

I reflect in stock, out of stock, or hidden state in what's shown to a shopper.

Shopping flow

This is the flow I'm building: product discovery within a genre-world → product detail → variant selection → cart → quantity/state management → checkout → payment → confirmation. Anything beyond it (wishlists, reviews, recommendations) is out of scope unless we agree to add it separately.

Payment integration

Razorpay handles the payment transaction itself. I build everything around it.

Checkout initiation

I move a cart into a payable checkout session.

Payment handling and verification

I handle the return from Razorpay and verify the payment server-side, rather than trusting the client.

Success / failure states

I build shopper-facing outcomes for both a confirmed and a declined or interrupted payment.

Order creation tied to verified payment

I create the order once payment is confirmed, not on cart submission alone.

Test/staging and production configuration

I keep separate Razorpay configuration so I can exercise the payment flow before it touches real transactions.

Customer accounts

Supabase Authentication provides sign-in. I wire it into the shop.

Authenticated vs. anonymous state

I build the shop to behave correctly whether or not a shopper is signed in.

Customer profile

I scope profile fields to the signed-in user.

Order history

I gate this behind sign-in, scoped to that customer's own orders.

Order system

Orders and line items

Each order I create records what was bought, tied to the customer who bought it.

Payment and inventory relationship

I tie a completed order to both a confirmed payment and a stock deduction.

Order state

I scope this to what the Phase 2 shop needs (paid, fulfilled), not a full order-management back office.

Production / QA

Staging environment

I exercise the full purchase flow, including Razorpay, in staging before it's live.

Production deployment

I deploy to production once staging is signed off.

Integration testing

I test product, cart, checkout, payment, and order creation together, not only in isolation.

Payment testing

I test successful, failed, and declined payments, and the resulting order and shopper-facing states for each.

Error handling and launch support

I handle interrupted or failed payments gracefully, and support the shop through launch.

Infrastructure vs. implementation

The services below sit outside my development fee. They're the platforms I build on, and some carry their own ongoing or per-transaction cost, set by those providers, not by me.

Infrastructure

  • Vercel: hosting/deployment platform. I run the initial build on its free tier.
  • Supabase: database, auth, and backend services. I run the initial build on its free tier; as traffic and, later, commerce volume grow, this typically moves to a paid tier, priced by Supabase and scaled to the site's own usage, separate from my quote.
  • Razorpay: payment infrastructure, with a per-transaction fee set by Razorpay.
  • YouTube: external media hosting for audio/video.
  • Domain: the existing yasandsass.in registration.

Implementation

  • I design the information architecture and experience
  • I implement the design system across genre-worlds
  • I design the database/schema and data relationships
  • I write the application logic connecting the frontend to Supabase
  • I implement every screen and component on the frontend
  • I build the third-party integrations (YouTube; Razorpay in Phase 2)
  • I wire up authentication and accounts (Phase 2)
  • I build the commerce flows: product, cart, checkout, orders (Phase 2)
  • I write the payment and order-state logic (Phase 2)
  • I build responsive behavior across breakpoints
  • I test across devices, flows, data, and integrations
  • I configure deployment and deliver to production

What my development fee covers

My quoted development fees are for designing and implementing the application, not for the underlying third-party services. Vercel, Supabase, Razorpay, and YouTube are infrastructure, the same infrastructure nearly any comparable product would sit on. My work is designing the architecture around those services: implementing the experience and, in Phase 2, the commerce flows described above, connecting genre and content data, and later product, order, and payment data, to the interface, handling application and payment state, testing the complete experience across devices and flows, and deploying a functioning production system.

The cost isn't set by the number of pages or by the retail price of the software services I'm using. It reflects the systems I'm designing and implementing in each phase, and my responsibility for delivering them as a working product, including the testing and fixes that happen before and after launch.
